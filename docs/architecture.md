# tickit architecture

tickit is a multiplayer issue tracker and wiki on lith v0.4.2: one Go binary, one SQLite file, server-rendered views pushed over SSE, Datastar 1.0.4 (Starbase's patched build with Rocket) in the browser. `docs/requirements.md` says what it must do; this file says how the code is cut, so that several people (and agents) can work on it at once without stepping on each other. Requirement IDs (FR-11.2, MP-08.3) are cited in code comments and test names where a test proves a criterion.

## Ids and keys

- Issues, pages, projects, spaces and comments have UUIDv7 strings as ids (time-ordered, so they satisfy lith's rule 10 and Q3). People see issue keys (`WEB-12`) and page titles.
- Persons: a guest is `g-` and 20 characters of base32 of SHA-256 of the session id; an account is `a-` and a UUIDv7; a seeded person is `s-` and a slug (`s-ada`). The session id never appears on a page, in an event or in a log line.
- Issue numbers per project come from the project's stream state (`project.number_assigned`); the guard table `issue_keys (key PRIMARY KEY, project_id, number, issue_id, UNIQUE (project_id, number))`, written by the command that creates or moves an issue, keeps them unique (NFR-18) and keeps every key an issue ever had, so old keys resolve after a move and a deleted issue's key answers 410 (FR-11, FR-12, FR-29).

## Identity and access

- `edge.Sessions` gives every browser an opaque session id. `people.Middleware` resolves it to an actor for the request: a login session row (`login_sessions`, keyed by SHA-256 of the session id, not expired) gives the account's person; otherwise the guest person derived from the session. `people.Actor(ctx)` returns it. GET never writes: a guest's row in `people` appears with the first command that needs it (`people.Ensure(tx, actor)`), and a guest's name and face derive from the id alone, so a guest without a row still renders.
- `access.Can(ctx, q, actor, right, scope)` answers from `scopes` and `memberships`, which commands write directly (no projector writes them; `access.AddScope` writes a scope with its creator as Admin). Every command that changes a project or a space checks its right inside `Apply` with `access.Require(tx, actor, right, scope)`, which refuses with an `*access.Denial`: a `*writer.Refusal` whose message says why, which the action answers with 403 (NFR-01). A scope the actor may not read answers `access.ErrNotFound`, as an unknown one does.
- Under Q14 a guest has Member rights in every open scope; staff log in. Site roles: none, moderator, admin.
- A view checks its right when a stream asks for it, and its key holds the scopes it shows. A change of membership or role applies to the person's open views at once (NFR-01.2): the routes that change one (`/cmd/projects/member`, `/member/remove`) call `rescope(person, project)` after the commit, which makes every view of each of the person's open streams again as they may now read it (the URL's views, the list the tab shows, the views its row added), swaps those whose key changed and takes off those they may no longer read. A page that lost one, or that shows the project (its board, backlog, settings or feed, one of its issues), gets `$_revoked` and loads again, so it shows what the new role may do, or answers 404. A site role or a deactivation ends the account's streams instead (`endWithLogin`).

## Actions

Every change is `POST /cmd/<area>/<action>` with a Datastar payload `{tab, op, ...}` (NFR-02). The handler, in `internal/web`:

1. checks the rate-limit class of the action per client address, then per person (DM-04, `edge.ClientKey`; the classes are in `internal/web/action.go`),
2. reads the payload with `sse.ReadSignalsLimit` and validates its shape (400 on malformed input, never 500, NFR-16),
3. takes the actor from the session, never from the payload (`tabs.By{Actor, Op, At}`, which commands carry and turn into `events.Meta` with `By.Meta()`),
4. checks that the tab's stream is open (`hub.HasStream`), waiting up to `web.Config.StreamWait` (2 s) for it, since a page posts some actions as it loads (the editor's open, a notification seen) while its stream opens, and answers 409 (`web.NotConnected`) without one: the outcome would reach no page, and every made-up tab id would be a row. `/cmd/watch` and `/cmd/list/view`, which write the tab's row too, check it as well,
5. runs `w.Do(ctx, writer.OnceResult(sid+":"+path+":"+op, tabs.Act{...Cmd: cmd}))` (the path too, so that another action naming the same op id never gets the first one's answer) and answers 204, or 403 when the command was refused for want of a right, or 400, 404, 409, 429, 503 for requests that reached no outcome.

In an area's handler that is `a, ok := s.decode(w, r, classField, &req)`, then `s.act(w, r, a, cmd)`. `OnceResult` rather than `Once`, so that a retry gets the first answer (a denial's 403, a result) while `tabs.Act` records refusals as outcomes either way.

`tabs.Act` gives a guest acting for the first time a row in `people`, runs the command in a savepoint and records its outcome in the tab's row whatever it was: the op id, and for a refusal its message and the field it belongs to (`tabs.Refuse(field, msg)`). The tab row keeps the newest 16 outcomes (not only the last), so two quick actions in one tab both settle. A refusal that implements `OutcomeData() json.RawMessage` adds `data` to its outcome: `tracker.Conflict` does, with who changed the field, when, both values and the version to resend with. The tab view patches them as the signal `_outcomes` (op id to `{ok, msg, field, data}`, `data` only when set), which the page's controls read to end their pending state (MP-09) and to show a refusal next to the control (`views.Act`, `views.Settle`, `views.Failed` build those expressions).

A command that went through can still have words for the page: `tabs.Act.Note` turns its result into the outcome's message and data (`s.runNoted`), as a bulk edit names the issues it refused (FR-58.2).

An action whose answer the page needs, such as the key of a new issue to navigate to, uses `s.actResult` and answers with a signal patch only (`_goto`), never with elements.

Login and logout are actions too (`POST /cmd/login`, `POST /cmd/logout`), outside `tabs.Act`: they answer with signals, the login form's message or `_goto`. The password is checked outside the writer (argon2id is too slow for it); the `people.Login` command checks again that nothing changed and writes the login session.

## Streams, views and topics

- Each document opens one stream, `GET /stream?tab=<tab>&v=<view>,<view>`, from `data-init` on `#stream`. Each `v` names a view factory registered by an area (`issue:<id>`, `issue-desc:<id>`, `desc-editor:<issue>.<tab>`, `desc-carets:<issue>`, `board:<projectID>`, `list:<query>`, `filters:`, `search:<query>`, `page:<id>`, `tree:<pageID>`, `pagedoc:<id>`, `editor:<page>.<tab>`) with `s.views.Register(kind, f)`, where `f(ctx, q, actor, arg) (live.View, error)` checks that the actor may read it (`access.ErrNotFound` answers 404, a denial 403, an unknown kind 400). Every stream also gets the person's view (`person:<id>`: name, bell, unread count), the demo view (`demo`: the reset notice), a `connected` view that hides "Reconnecting", the session's prefs view (`prefs:<tab>`, the signal `_prefs`), and the tab view last. The page's views reach `openStream` as the signal `_views`, never inside an expression.
- The stream's `Spec.ID` is `<personID>.<tab>`, so `hub.Watchers(key)` yields who watches a view without a read (MP-01, MP-02). A kind registered with `s.views.RegisterWithPresence` makes every stream that watches one of its views watch `presence:<key>` too: a shared view with `Presence: true` that lists one face per person in the order they came, with the tab count in the tooltip. The page puts `views.Presence(views.PresenceID(key), nil)` where the row goes (a shared `ui.PresenceRow`); the document's own style puts the viewer's face first, outlined, and shows at most 8. `RegisterWithPresenceOf(kind, f, of)` lets views of many keys share one row: every page's tree view (`tree:<space>:<page>`) joins `presence:pages-in:<space>`, the row above a space's tree (MP-02.1), every window of the home feed (`activity-home:<from>`) joins `presence:home`, and every grid of a dashboard, whatever its reader reads, `presence:dashboard:<id>`. The first-visit hint (DM-11) says "Open this page in a private window" on a page one of whose views joins a row (`Shell.Present`), and points to a board, an issue or a page elsewhere.
- A face shows away, dimmed with "away" in its tooltip, after 5 minutes without input in any of the person's tabs (MP-02.4). GET never writes, so the page reports input with `POST /cmd/input {tab, op}` (caret class, sent without waiting) at most once a minute while there is input and at its stream's first heartbeat; it goes into `presence_input` (person, last input; migration 081), and a report within half a minute of the last writes nothing. A presence row reads it for the faces it shows and declares `away:<person>` for each (`live.Depends`), so that it renders again for those people only: `people.Input` touches the topic when someone comes back, `Server.PresenceJobs` (cmd/tickit runs it) every 5 s for those who turned away, without a write. A report from a tab without an open stream counts for nothing.
- The server keeps the open streams by ID (`alive.go`: the person, the session, the tab, the views the URL named): the state of a connection, gone with it, beside the hub's. A page answers each heartbeat (`$_ping`, every 20 s) with `POST /alive?tab=` (outside `/cmd/`, Datastar's header checked, limited per address and stream), and a stream that opened with `alive=1`, as every page's does, ends once none came for `web.AliveTimeout` (50 s): a connection that dropped without closing kept its stream for minutes before, since the server's writes go into the kernel's buffers and no write misses its deadline, and Caddy in between hides it as well. Its faces leave the rows within a minute (MP-02.3). A stream that ends, unless another with its ID replaced it, takes its tab's typing indicators with it (`tracker.EndTyping`, MP-07.4); it writes only when the tab had one up.
- An address holds at most `web.MaxStreamsPerAddr` (40) streams, counted by the hub (`live.Spec.Client` is `edge.ClientKey(r)`, `live.Options.MaxStreamsPerClient`; 429 beyond, which the page's `retry: 'error'` tries again), and opens them at one a second after a burst of as many, beside the hub's 200 (NFR-41). Loopback without a proxy's header (a probe, the load test) counts under no client. An account's stream ends once its login session no longer resolves to the account (`LoginCheck`, NFR-04.2).
- A page that falls behind its stream is paced by it (`pace.go`, as lith's template does): `newest-frame.js` dispatches `newest-frame-behind`, which `<body>` posts to `POST /pace?tab=` (never from the stream's element, whose request it would abort); the hub then sends that stream a write only once the page has acknowledged the last, through the element each paced write ends with, which posts `POST /ack?tab=&s=&n=&rtt=` after the paint (`live.Spec.Ack`, `Hub.Pace`, `Hub.Ack`), and every frame again once the page keeps up for 5 s. Both are limited per address, then per session (`/pace`) or stream (`/ack`), answer 204 over their limits, and reach only the streams of the request's person (the stream's ID); they sit outside `POST /cmd/`, with Datastar's header checked by `edge.CSRF`. `tickit_live_newest_frame_behind_total`, `_paces_total`, `_releases_total` and `_acks_total` count them. The tab's and the prefs' views are keyed by tab and a hash of the session, an editor's by tab and person, so a forged tab id gets views of its own (NFR-02.3).
- A side panel or a tab switch adds a view to the open stream with `POST /cmd/watch` (`hub.Watch`), and records it in the tab row so that a reconnect restores it; `POST /cmd/unwatch` takes it off.
- A view's key holds everything its render depends on. Shared views render nothing about the viewer; per-viewer parts go in `tab:<id>`, `person:<id>` or signals.
- Topics form a tree by their `:` segments (lith v0.4.0): a commit to `board:42` marks the views on `board` too. No view listens to a bare root that has children: the shared roots (`issues`, `projects`, `pages`, `spaces`, `people`, `search`, `filters`, `demo`, `moderation`) have none, the per-id topics have roots of their own (`issue`, `project`, `board`, `page`, `person`, ...) that no view lists bare, `lith:events` is a sibling of the runner's `lith:projection:<name>`, and the per-tab, session and presence state is under roots of its own (`tab:<id>`, `prefs:<hash of the session>`, `editor:<tab>`, `carets:<page>`, `desc-editor:<tab>`, `desc-carets:<issue>`, `issue-typing:<id>`, `away:<person>`; presence views list `people` alone and declare the `away:` topics of their faces). A new topic keeps it so: a view on a level above many topics renders at each of their commits.
- Topics: `project:<id>`, `projects` (any change to any project: the project list, pickers), `issue:<id>`, `issues` (any change to any issue or issue comment: lists, search, chips, open counts), `board:<projectID>` (a project's board and backlog), `filters` (saved filters), `space:<id>` (a space and its page tree), `page:<id>` (a page's head, versions, links, comments), `pagedoc:<id>` (every commit to its document), `inline:<id>` (its inline comments: a new one, a resolution, a detached anchor, any change to a comment on the page), `issuedoc:<id>` (every commit to an issue's description), `chips:<id>` (what its chips, mentions and page links show), `carets:<id>` and `desc-carets:<id>` (its editors' presence), `editor:<tab>` and `desc-editor:<tab>` (an editing tab's row), `pages` (any page change), `spaces`, `person:<id>`, `people` (names and faces), `tab:<id>`, `demo`, `dashboards` (the list of dashboards), `dashboard:<id>` (a dashboard's name and gadgets), `recent:<person>` (what the person viewed), `images` (an image uploaded, hidden, shown again or deleted). A command touches every topic whose views it changes.

## Pages and the document

A page handler answers with `s.render(w, r, status, build)`, where `build` reads in the request's one read transaction and returns a `web.Page`:

```go
return Page{
	Title:      "Board",                 // the document's title adds "tickit"
	Nav:        "projects",              // the header link marked current (ui.MainNav), or "moderation", "admin"
	Sidebar:    ui.SideNav(sideNav),     // nil for none; SidebarLabel names it ("Project" by default)
	Width:      "full",                  // "" (80rem), "prose" (46rem), "full"
	Views:      []string{"board:" + id}, // the stream's views, besides the person's, the demo's, the prefs' and the tab's
	Components: []string{"select"},      // Starbase components, loaded with what they render (docs/design-system.md)
	Body:       views.Board(b),
}, nil
```

`Query` fills the header's search box, `Scripts` loads further modules by their static name, and `Create` replaces the header's create dialog (id `views.CreateID`; by default `s.render` puts `views.CreateIssueDialog` there, "Create dialog" below). `views.Layout` renders the rest: the head with the bundle, the favicon, the font preloads, the import map with the CSP nonce, Datastar and `newest-frame.js`; `#stream`; `ui.Shell` with the header, the demo notice, the first-visit hint (DM-11) and the footer; "Reconnecting" (MP-10.1) and `$_problem` as floating notices.

Display preferences (theme `system`, `dark` or `light`; style `pixel` or `smooth`; density `comfortable` or `compact`; a dismissed demo notice; a dismissed hint) are the session's row in `prefs` (`tabs.Prefs`, `tabs.GetPrefs`). `POST /cmd/prefs {tab, op, key, value}` sets one through `tabs.Act` (`tabs.SetPref`, 400 for an unknown key or value) and touches `tabs.PrefsTopic(sid)`; every stream watches `tabs.PrefsView`, which patches `$_prefs`, and the document puts it on `<html>`, so every tab of the session follows. GET draws them from the first byte (`ui.Prefs`); no cookie carries them (NFR-31).

A person's face is `ui.FaceOf(id)`, and their hue an index of 0 to 15 (`people.Person.Hue`, `data-hue`; the stylesheet turns it into degrees, times 22.5). `views.UIPerson` is the one place that makes a `ui.Person` of a `people.Person`; seeded people keep their own hue.

## The issue page

`GET /{key}` (`/WEB-12`, any case) is the issue's page; another spelling or an old key answers 301 to the key now, an unknown key 404 with a search box, a deleted issue's key 410 with who deleted it and when, and `/ticket/<id>` and `/dashboard/<id>` 301 to the key (FR-12). The page is a static frame (`views.IssuePage`, `issueFrame`) holding the regions of three views:

| View spec | Key | Topics | Renders |
| --- | --- | --- | --- |
| `issue:<id>` (with presence) | `issue:<id>` | `issue:<id>`, `people`, `project:<project>`; again every 30 s for relative times | `#issue-main`, `#issue-desc` (the description's heading), `#issue-related`, `#issue-side`, `#issue-comments`, `#issue-history`, `#issue-activity`, `#issue-mentions`, and the signal `$_is.max` (the version) |
| `issue-desc:<id>` | `issue-desc:<id>` | `issuedoc:<id>`, `issue:<id>`, `people` | `#issue-desc-body`: the description as it is now, at every commit (FR-15, MP-03) |
| `issue-typing:<id>` | `issue-typing:<id>` | `issue-typing:<id>`, `people`; every second | `#issue-typing-summary`, `#issue-typing-description`, `#issue-typing-comment` (MP-07) |
| `issue-at:<id>.<v>` | `issue:<id>:at:<v>` | `people` | `#issue-asof`: the issue at version v (FR-70); tabs at one version share it |

The regions are siblings, never nested, since a patch skips an element inside a `data-ignore-morph` one. Fields people type in are in the frame (the comment box) or marked `data-ignore-morph` with their value in a `_is` signal (the editors in place), so no frame resets them. Elements the morph would reset keep their state with `data-preserve-attr` (`hidden`, `aria-busy`, `disabled`). Comments, History and Activity are Starbase's sb-tabs (`ui.Tabs`) in the frame, their regions in its slots; the selected tab is `$_is.tab` (`data-attr:selected`, `sb-tab-change`), and every page with the issue's frame, the issue's page and those with the panel, loads the component (`web.panelComponents`).

The page's state is the signal `_is`: the issue's id and key, the viewer's id, and per field the pending op (`ops`), the refusal (`msg`), a conflict's data (`conflict`), a request with no outcome (`fail`) and the value sent (`want`). Every change is `POST /cmd/issues/{id}/{field}` with `{tab, op, seen, value, ref}` through `tabs.Act`; `seen` is the version the control showed (a menu keeps the version it opened at). The fields: `summary`, `type`, `status`, `priority`, `assignee` (`me` for the actor), `parent`, `due`, `points`, `estimate`, `remaining` ("2h 30m"), `sprint`, `labels` and `components` (`ref` add or remove), `watch` (toggles), `link` (`value` a key, `ref` the link type), `unlink`, `pagelink` and `pageunlink` (`value` a page's id, FR-102: "Link page" searches with `GET /issues/link-page?q=`), `subtask`, `comment` (markup, `markup.Comment`), `cedit`, `cdelete`, `chide` (`ref` the comment's id), `delete`. `POST /cmd/issues/{id}/typing {tab, op, field, stop}` is a caret-class action sent without waiting: it writes `issue_typing` (migration 011) and touches `issue-typing:<id>`; an indicator goes 5 s after the last keystroke, and a save, a cancel, a comment, leaving the comment box or the end of the tab's stream ends it at once (the row keeps the tab that typed). Controls in the regions carry `data-act`, `data-field`, `data-value` and `data-ref`, and the frame's one delegated handler runs them, so frames carry attributes rather than expressions. The assignee, the epic and the due date are Starbase pickers (`data-act="pick"`, docs/design-system.md, "Starbase components"): the frame's `sb-change` handler sends their value, with the version the page showed when the picker took the focus.

The description is co-edited in the page editor (FR-15, docs/editor.md, "Issue descriptions"): Edit (`data-act="desc-edit"`) fetches the editor's host from `GET /issues/{id}/description/editor` into `#issue-desc-editor`, a part of the frame the issue's page has and the panel has not (the panel's Edit opens the page with `?edit=description`); `POST /cmd/issues/{id}/description/open`, `/close`, `/commit` and `/presence` are its actions, and `desc-editor:<issue>.<tab>` and `desc-carets:<issue>` its views, which open records in the tab's row. `GET /issues/{id}/description?v=<version>` compares the description a version made with the one before (the history's Compare).

What the shared views cannot know about the viewer comes from the document: `viewerStyle` shows the viewer's own comments' Edit and Delete, the watch button's state, and hides the viewer's own typing indicator and "Delete issue" outside the projects where the viewer may delete issues (`views.Deletes`, by `#issue-main[data-pid]`); `$_is.ro` makes a Viewer's page read-only (comments stay open) and `$_is.mod` shows Hide to a project's Admin or a moderator. A comment's draft stays in the tab across a reconnect and a reload (`sessionStorage`, which is per tab).

## Issue panel

From a board, a list or a search, an issue opens in `ui.SidePanel` beside the page (FR-13.2). To wire it:

1. Put `@views.IssuePanel(me.ID, moderates)` once in the page's body (`moderates`: `access.SiteCan(me, access.Moderate)`).
2. Give every link to an issue the issue's id in `data-issue-panel`: `<a href="/WEB-12" { views.IssueLinkAttrs(issue.ID)... }>`. Keep the `href`: a click with Ctrl, Cmd, Shift or Alt, a middle click, or a page without the panel follows the link to the issue's page.

A plain click opens the panel, puts the issue's URL in the address bar (`history.pushState`) and adds `issue:<id>` and `issue-typing:<id>` to the tab's stream with `POST /cmd/watch`; the stream fills the panel's regions with the same view the issue page shows. Escape, the close button, a click beside the panel or the browser's Back close it: the views come off the stream (`POST /cmd/unwatch`) and the page's own URL comes back. The page never left, so its filter, its page and its scroll position stay. The page needs no view of its own for the panel and no route.

## Create dialog

`views.CreateIssueDialog` is the header's create dialog (FR-10), with the id `views.CreateID`, so the header's Create opens it (`command="show-modal" commandfor="create"`). `s.render` puts it on every page whose `Page.Create` is nil: it lists the projects the person may create issues in and preselects `Page.Project` (a project's id: set it on a board, a backlog or a project's list), else the first. A board column's "+" opens it with that column's status: give the button `data-on:click={ views.CreateWithStatus }`, `data-status="<status id>"` and `data-project="<project id>"`. `POST /cmd/issues/create {tab, op, project, type, summary, description, priority, assignee, labels, parent, status, stay}` answers `$_goto` to the new issue, or, on a page with the issue panel (`stay`), opens the new issue in the panel. A refusal stays next to its field (`$_new.field`, `$_new.msg`) with what the person typed.

## Event sourcing

- Streams: `project`, `issue`, `issuedoc` (an issue's description, docs/editor.md), `space`, `page`, `pagedoc` (a page's document), `comment` (issue and page comments), `inline` (an inline comment's range and resolution, keyed by the comment's id, FR-91). Kind and type names are permanent once the demo runs.
- Each domain package exports `Parts() []events.Part` (its projectors and upcasters); `cmd/tickit` builds one `events.Store` from all of them and starts one `events.Runner`. A package whose commands append events also exports `Bind(*events.Store)`, which `cmd/tickit` calls with that store, so that every package's projectors of a stream kind run in the commands that append to it; without it (tests, tools) the package's commands use a store of its own parts alone.
- Deciders decide from the stream's state row, never from a projection. Pages render from projections. Inline projectors keep read models; reactions (notifications) are catch-up projectors that send their command with `writer.Once` keyed by the event's position.
- Every event carries `Meta{At, Actor: personID, Causation: opID}` (FR-155).
- Per-field conflicts (MP-08): an issue's state row records, per field, the stream version that last changed it (`IssueState.Changed`). Who changed it and when are that event's metadata, which the command reads from the log when it refuses (an `Evolve` sees no metadata); the value is the field's value in the state. A change carries the version the page showed (`Seen`); it applies when its field has not changed since, or when the last change was the actor's own, and is refused otherwise with the message of MP-08.3 as a `*tracker.Conflict`.

## The tracker

`internal/tracker` holds the Jira side; its package documentation lists the API.

- Streams and their event types (permanent): `project` (`project.created`, `.edited`, `.archived`, `.unarchived`, `.component_defined`, `.component_removed`, `.number_assigned`, `.wip_limit_set`, `.sprint_created`, `.sprint_started`, `.sprint_completed`, and the workflow's and the board's `.status_added`, `.status_renamed`, `.status_category_set`, `.statuses_ordered`, `.status_removed`, `.transition_rule_set`, `.column_added`, `.column_renamed`, `.columns_ordered`, `.column_removed`, `.status_mapped`), `issue` (`issue.created`, `.summary_changed`, `.description_changed`, `.type_changed`, `.status_changed`, `.moved`, `.priority_changed`, `.assignee_changed`, `.parent_changed`, `.due_changed`, `.points_changed`, `.estimate_changed`, `.remaining_changed`, `.sprint_changed`, `.labels_changed`, `.components_changed`, `.watchers_added`, `.watcher_removed`, `.link_added`, `.link_removed`, `.deleted`, `.project_changed`, `.hidden`, `.unhidden`, `.page_linked`, `.page_unlinked`, `.category_changed`), `comment` (`comment.added`, `.edited`, `.deleted`, `.hidden`, `.unhidden`; a comment names its subject, `issue` or `page`), `issuedoc` keyed by the issue's id (`issuedoc.created`, `.committed`, `.snapshot`: internal/collab's). `issue.description_changed {to, mentions_added, upto, editors}` is a version of the co-edited description, cut from its `issuedoc` stream (`upto`) by `CutDescriptions` or at once by `SetDescription`. Statuses have stable ids (`todo`, `inreview`) and names; issues and URLs hold the ids.
- Workflows and board columns (FR-36, FR-37, FR-43, `workflow.go`) live in the project's stream. `ProjectState.Workflow` holds the statuses in order, the start status and `Follows` (a status to the statuses an issue may come to it from; a status without an entry follows any), `ProjectState.Board` the columns in order, each with its statuses in workflow order and its limit, and `Retired` the ids of removed statuses, which are never given again (a new status's id is a slug of its name: "In QA" is `in-qa`). A project starts with `DefaultBoard`: a column per status but Backlog, keyed and named as its status, so `/cmd/projects/wip {status}` names a column by its id. Each event says all it changes: the decider emits a rename of the columns named as a renamed status, the removal of a column a removed status leaves empty, and the columns' new order when a status moves on a board whose columns were in workflow order. A status's removal (`RemoveStatus {status, move_to}`) is one command: it reads the issues that hold the status from the projection, refuses without `move_to` when there are any, and appends `issue.status_changed` to each, so the move shows in its history; a category change (`SetStatusCategory`) appends `issue.category_changed` to each issue that holds the status, which moves its resolved time (FR-38). The rules are enforced in the issue's deciders (`decideEdit` for the menu and bulk edit, `decideMove` for the board), refusing with `followRule`'s sentence: "Done can only follow In Review." A board move names a column (`Move.Column`), and the decider picks the card's own status when the column holds it, else the column's first status the rules allow (`columnStatus`).
- A command reads the states it decides on with a decider that appends nothing (a peek), checks its right with `access.Require` against the issue's project, then executes. Creating an issue appends to the project's stream (the number) and the issue's in one savepoint; a link appends to both issues; a comment appends to its stream and adds watchers on its issue's.
- The seed acts as seeded people (`people.Seed`) with a past `By.At`; the tracker's access checks let them, since no request acts as one.
- Ranks are fractional indexes (`RankBetween`), one order per project shared by the board's columns and the backlog. A move names its neighbours by id; the command reads their ranks, and the project's last rank for a new issue, from the `issues` projection and hands them to the decider. This departs from "deciders decide from the state row": a rank is no rule, and a stale neighbour only places a card beside another one, so ranks need no guard table.
- Rules across issues live in tables the commands write: `issue_keys`, `issue_parents` (children counts for type changes, deletes and moves, FR-19.2), `tracker_actors` (who acted in a project when: assignable for 24 hours, FR-17.1). Saved filters (`saved_filters`, `saved_filter_stars`) are relational.
- Projections: `tracker_projects` keeps `projects`, `statuses` (workflow order, the board column that shows each, `follows` as JSON or '' for any; a removed status keeps its row with `removed = 1`, so history and feeds still name it), `board_columns` (order, name, limit; migration 085), `components`, `sprints`; `tracker_issues` keeps `issues`, `issue_labels`, `labels`, `issue_links`, `issue_watchers`; `tracker_comments` keeps `comments`; `tracker_descs` (on `issuedoc`) keeps `issue_doc`, the head of each description. `issue_editors` is the tabs editing a description, written by its commands. A project's open issue count is counted from `issues` when read, and an issue's status order is joined from `statuses`: a table belongs to one projector, which sees one stream kind, and a workflow reordered later (FR-36) then changes no issue row.
- Search matches text with `instr` on a lower-case column that Go fills (keys, summary, description text; comments have their own), so `%` and `_` match themselves and case folds beyond ASCII. Every filter runs in one statement whose lists are JSON parameters (`json_each`); each sort has its own ORDER BY.

A drag (a mouse anywhere on a card, a finger on its grip) or the card menu (Move to a column, Move up, Move down, Open; NFR-47) moves the card's list item to its new place at once and marks it pending (`data-state`, kept through morphs by a MutationObserver: the frames know nothing of it), then posts the move with the card's version (`data-v`) and its new neighbours, with `requestCancellation: 'disabled'`. One view renders every row: lith renders a view as one frame, and the morph changes only the elements that differ, so a view per row would add streams' views without saving bytes.
- The frame of a hundred cards stays under 60 KB (NFR-37.1): cards are `ui.BoardCard` (flat list items), their glyphs masks of `ui.Glyphs` (once in the page) and their faces masks of `ui.FaceStyles` (in the frame); a card carries its issue's id in 22 characters (`data-i`), which the page turns into `data-issue-panel` when the card is clicked, so the issue opens in the panel. ## Activity and the home page

`internal/activity` reads feeds from `lith_events` and stores nothing (FR-69): windows going back from the head (512 positions, doubling, at most 20,000 positions), in which each source's stream kind is read by the log's index of positions and only the rows of the types it names are decoded with the domain's streams (a co-edited page's commits, most of the log at NFR-38's load, are never read), kept when the person may read their subject's scope, consecutive edits of one page by one person within 10 minutes as one entry (FR-69.3). `activity.Home(readable)`, `activity.Project(id)`, `activity.Space(id)`, 50 a page; `activity.Mine` is what a person changed lately. Sources are registered per stream kind (`tracker.go`); the wiki adds its page stream and `commentSubjects["page"]` in one file, `internal/activity/wiki.go`.

- Views: a feed is a window of 50 entries (`activity.PageSize`) from `<from>`, a multiple of 10 (`views.FeedStep`) up to 950 (`web.maxFeedEntries`, 1,000 entries deep): `activity-home:<from>` (key `activity:home:<hash of the readable scopes>:<from>`, shared by everyone who reads the same scopes and is at the same window; with presence: the home page's row), `activity-project:<id>.<from>` and `activity-space:<id>.<from>` (`<id>` alone is the window from 0; key `activity:<kind>:<id>:<from>`); topics `issues`, `projects`, `pages`, `spaces` and `people` (`web.feedTopics`: what the events a feed shows touch; a page comment touches `pages` for them), rendered again every minute for relative times. Not `lith:events`, which every append touches: co-editing appends many commits a second, and a feed shows a page's versions, never its commits. A window reads the feed's first `from + 50` entries with `activity.Feed` and renders the last 50 of them, with the total as far as the read went (`views.ActivityFeed.Total`, `Known` once the feed ends). A project's or a space's page renders `views.Activity(feed)` from `s.ScopeActivity(ctx, q, scope, from, now)` and names `views.FeedSpec(feed.Kind, feed.Scope, feed.From)` in `Page.Views`, with the components `web.feedComponents` and the script `views.FeedScript`.
- Scrolling (`routes_feed.go`, `views.FeedWindow`, `static/feed/feed.js`): the feed is `sb-virtual-scroll` with `role="feed"`, one article a row of `--tk-feed-row` with `aria-posinset` and `aria-setsize` (-1 while more may follow), faces and glyphs as masks (`ui.FaceStyles`, `ui.Glyphs`), so a window's frame stays under 50 KB (NFR-37). When the component asks for entries outside the window (`sb-window`), the page posts `POST /cmd/feed/window {tab, views, feed}` (class view): the handler resolves the new window as the person may read it, keeps it in the tab's row (area `feed`, for `rescope`), and after the commit, in commit order, unwatches the window the stream watched (the one `$_views` named, or the one the row moved to) and watches the new one; the page puts the new name in `$_views` for a reconnect. The window is per tab, in the view's name, never in a shared view. Windows count from the newest entry, so a new entry moves every entry of every window down by one in their next frames. The articles carry `data-key` (no id, so the morph patches them in place), and the component keeps the keyed entry at the top of the box, and the focus on its entry, when the reader scrolled or has the focus or the pointer in the feed; at the top and idle, new entries come in. feed.js shows "Newer activity" once entries arrived above, which leads back up, and moves the focus entry by entry with Page Down and Page Up (the ARIA feed pattern). Without script, or for a reader who prefers them, "Newer activity" and "Older activity" link the windows by `?from=` on the page's address.
- The home page `/` (FR-59, `routes_notify.go`): the person's work in the view `home:` (key `home:<person>`: counts, open issues assigned to them, "recently edited by you" from the log, the projects and spaces they may read) and a window of the home feed (`?from=n`, "Scrolling" above). The `home:` view is per person and renders on every change to an issue, a project, a page or a space, and on the person's own topic (a membership), so its reads stay cheap at NFR-38's load: `activity.Mine` lets SQLite filter the log by actor and skips a person without a row in `people` (who never acted), "assigned to me" reads `issues_assignee`, and the projects with their open counts (`issues_project_open`, migration 072) come from `web.projectsCache`, kept against the hub's version of `projects` and the projects' `project:<id>` and `board:<id>` (lith's `Hub.Version`, `Seq(ctx)`; the home views that miss it in one tick share one read). The spaces give their names only. "Recently viewed" (FR-59.1) comes from `recent_views` (migration 079, `internal/recent`): GET never writes, so the issue page, the issue panel and a wiki page post `POST /cmd/notify/seen {subject, kind}` once as they open (`views.Viewed`), which marks the person's notifications of the subject read and, for `kind` "issue" or "page" of something the person may read, records the view (`recent.Record`, the newest 20 per person; `recent.Sweep` in the hourly sweep drops those older than 30 days). The home view listens to `recent:<person>` too.

- A click on a row or its summary opens the issue in the side panel (FR-50.3, "Issue panel"): the list's body holds `views.IssuePanel` and each summary link `views.IssueLinkAttrs`; so do the results of `/search`. `GET /issues.csv?<query>` exports the whole result (FR-152). `/search` with a list's filter and no text (`/search?assignee=me`) redirects to `/issues` with it.
- Bulk edit (FR-58, `routes_bulk.go`, `views/list_bulk.*`): each row of the shared list has a box (`.list-check`, the issue's id in `data-i`) and the head one for the page; the selection is the tab's own signal `$_bulk.ids`, at most 100 issues, kept across the list's pages and filters, and the list's container checks the boxes from it after every frame (a `MutationObserver`) and every change of it. (an issue the actor may not read is not named), with the refused ids in `data`, which stay selected; with every issue refused it is a refusal, and a denial (403) when each was for want of a right. ## The wiki

`internal/wiki` holds the Confluence side; its package documentation lists the API, and docs/editor.md says how co-editing works.

- Streams and their event types (permanent): `space` (`space.created` with its home page, `.edited`, `.archived`, `.unarchived`), `page` (`page.created`, `.renamed`, `.moved`, `.labels_changed`, `.watched`, `.trashed`, `.restored`, `.deleted`, `.version_cut` with the version's title and document; never folded), `pagedoc` keyed by the page's id (`pagedoc.created {epoch, doc}`, `.committed {ref, client, base, steps}`, `.snapshot {epoch, doc}`). Page comments are the tracker's `comment` stream with subject `page` (`tracker.RegisterSubject`: rights in the page's space, replies one level deep, `CommentAdded.Parent`); the wiki keeps their threads in `page_comment_threads`. An inline comment (FR-91, docs/editor.md, "Inline comments") is a page comment with a stream `inline` keyed by its id (`inline.anchored {page, v, from, to, quote}`, `.resolved`, `.reopened`).
- Rules across pages live in tables the commands write: `page_titles` (titles unique per space without case, a trashed page keeps its title), `page_parents` (no move under a descendant; children move up when their page goes to the trash), `page_editors` (the editing tabs: ack, selection, seq, the last refusal), `page_anchors` (each inline comment's range in the head document, mapped by every commit in its command, detached once its text is gone; the fold drops the commits a rebuild would need, so it is no projection). Space keys are unique through access's scopes.
- Projections: `wiki_spaces` (`spaces`), `wiki_pages` (`pages` with parent and fractional rank, `page_labels`, `page_watchers`), `wiki_versions` (`page_versions`), `wiki_docs` (`page_doc`: epoch, head version and ref, the document as of a checkpoint every 50 commits; `page_chips`, `page_links`), `wiki_threads`, `wiki_inline` (`page_inline`: an inline comment's page, range as made, quote and resolution), `wiki_chips` (on the issue stream; writes nothing, touches `chips:<page>` of the pages that show the issue, FR-100.2), `search_pages` (each version's text, FR-57). Projections store documents as internal/doc writes them, never the stored event's escaped JSON, so a rebuild equals the live tables.
- Commands: `CreateSpace`, `EditSpace`, `ArchiveSpace`; `CreatePage` (counted against the demo's daily cap), `RenamePage`, `MovePage`, `SetPageLabels`, `WatchPage`, `TrashPage`, `RestorePage`, `DeletePage`; `AddComment` (then the tracker's `EditComment`, `DeleteComment`, `HideComment`); `AddInlineComment`, `ResolveInline` (FR-91); `OpenEditor` with `WatchEditor` after it, `Presence`, `CloseEditor`, `Commit`; `CutVersion` ("Save version"), `SetDocument`, `RestoreVersion`; the jobs' `CutDue`, `Fold` and `SweepEditors`, which `web.Server.WikiJobs` sends (cmd/tickit runs it beside the sweep).
- A commit runs outside `tabs.Act`: `POST /cmd/pages/{id}/commit` runs `demo.Guard(wiki.Commit)`, which applies a resent commit once by its ref among the commits since its base (no op id per commit, NFR-43.2), and answers 204, 409, 422, 403, 429 or 503. The editor confirms a commit by its ref in the next frame, so no tab row is rewritten and no outcome sent ten times a second; a refusal by a rule goes into the editing tab's `page_editors.refusal`, which its view renders. Presence posts are `w.Send`.
- Views: `page:<id>` (head, linked issues and pages, comments), `pagedoc:<id>` (the reader's body from the document cache, re-rendering the changed blocks only; keyed by the page and a hash of the projects the reader may read, for its issue lists), `pagelists:<id>` (on the editor's page: the issue lists' rows and the saved filters for the editor's node views, keyed the same way), `pagepeople:<id>` (presence, editors marked: the tabs that watch `carets:<id>`), `tree:<pageID>` (the space's tree with that page current and its ancestors open; tabs open and close nodes, which `data-preserve-attr` keeps), `history:<id>`, `inline:<id>` (its inline comments beside the text, in view and in the editor; the highlights come with `pagedoc:<id>` and each editor's frame), `trash:<space>`, `spaces`, and on the editor's page `carets:<id>` (shared, with Presence: the signal `$_carets`, which each host's `carets` attribute follows), `pagetitle:<id>` (the signal `$_wkTitle`) and the tab's own `editor:<page>.<tab>`, which `OpenEditor`'s handler adds with `hub.Watch` and the tab's row restores after a reconnect.
- Issue lists on a page (FR-104, `routes_embed.go`): an `issue_list` block names a saved filter or a filter in the issue list's query syntax and a row cap. The reader view renders its rows with `tracker.Search` as the reader may see them, "me" being the page's creator. A render of a page with lists declares `issues`, `projects` and `filters` (`live.Depends`), so a page without lists does not render on every issue change. `listsCache` keeps a list's HTML by list, readable projects and creator against `Hub.Version`, so one list renders once a tick for every page and reader of the same rights. Versions and compare show a list's filter (`doc.ListDescription`).
- `POST /cmd/pages/issue {tab, op, page, project, summary, find, block, nth}` (FR-105, class create, counted as a new issue for DM-04.3) creates a task from a page's selected text, links the page (`tracker.LinkPage`) and, in view mode, puts the chip in place of the text (`wiki.ChipSelection`). It needs the right to edit the page and to create issues in the project, and answers `$_pissue.key` and `$_pissue.chip`; in the editor the editor puts the chip in itself.
- Pages linked to an issue by hand (FR-102) are `issue.page_linked` and `issue.page_unlinked` on the issue's stream (`tracker.LinkPage`; the action checks the page's right), kept in `issue_pages` (migration 078) by the tracker's issues projector, which touches `page:<id>`; `wiki.PagesLinkedToIssue` and `wiki.IssuesLinkedTo` read it, the page lists the issues under "Linked issues" with its chips, and the chips projector touches `chips:<page>` of linked pages too.
- For the issue page: `wiki.PagesMentioning(ctx, q, key)` and `wiki.PagesMentioningIssue(ctx, q, issueID)` (FR-101); the wiki touches `issue:<id>` when a page's chips of the issue come or go, or the page is renamed or trashed.
- Hooks in other packages, one file each: `internal/notify/wiki.go` (page comments notify the page's watchers, FR-114; a version mentioning someone new tells them, FR-112), `internal/activity/wiki.go` (pages created and edited, a version an entry), `internal/demo/wiki.go` (the seed's spaces, pages, versions and comments; pages as moderated; the cap of pages).

## Search

`internal/search` is the search across issues and pages (FR-57), an FTS5 index that is a projection of the event streams (NFR-44).

- Each kind of document has two tables (`search.Tables(kind)`, `migrations/060_search.sql`): its rows (`search_issues`, `search_pages`, `search_comments`: id, scope, key and old keys, the folded title, href, place, labels and people as JSON, hidden, updated) and their text in an FTS5 table beside them (`<table>_fts`: key, title, body; `unicode61` without diacritics, prefix indexes of 2 and 3). The row's `n` is the text's rowid.
- Only one projector writes a kind's tables, through `search.Put(tx, kind, doc)`, `search.Patch(tx, kind, id, func(*search.Doc))`, `search.Hide(tx, kind, id, hidden)` and `search.Remove(tx, kind, id)` in its inline handlers. A handler builds the document from its event and from the document as indexed (`Patch`), never from another projection, which may be rebuilding at the time. Each write touches `search.Topic` (`search`).
- The tracker's parts hold two of them: `search_issues` on the issue stream (created, summary, description, assignee, labels, moves to another project with the old key kept, deletes) and `search_comments` on the comment stream, which indexes comments on issues and on pages (scope: the subject's id, key: its kind; a hidden comment stays indexed but out of results).
- The wiki's projector of its page stream, in `wiki.Parts()` (`internal/wiki/search.go`), named `search.PagesProjector` at `search.PagesVersion`, writes `search.Tables(search.Page)`; in outline:

```go
var pageSearch = events.NewProjector(PageStream, search.PagesProjector, search.PagesVersion,
	events.Handle(PageCreatedType, func(tx *writer.Tx, r events.Record[string, PageCreated]) error {
		return search.Put(tx, search.Page, search.Doc{ID: r.ID, Scope: r.Data.Space, Title: r.Data.Title, Body: text,
			Labels: labels, People: []string{r.Actor}, Place: spaceKey, Href: pageURL, Updated: r.At})
	}),
	events.Handle(PageRenamedType, func(tx *writer.Tx, r events.Record[string, PageRenamed]) error {
		return search.Patch(tx, search.Page, r.ID, func(d *search.Doc) { d.Title, d.Updated = r.Data.To, r.At })
	}),
	events.Handle(PageDeletedType, func(tx *writer.Tx, r events.Record[string, PageDeleted]) error {
		return search.Remove(tx, search.Page, r.ID)
	}),
	// every other type of the stream: events.Ignore
).Tables(search.Tables(search.Page)...)
```

  `Scope` is the space's id (the scopes row that access reads), `Place` what results show beside the title (the space's key), `Href` the page's address, `Body` the plain text (`tracker.DocText` reads a document's), `People` who a person filter finds it by (author, editors). A page moved to another space patches Scope, Place and Href. Page comments need nothing more: they are comments.
- `search.Search(ctx, q, search.Query{Text, Kinds, Projects, Spaces, InProjects, InSpaces, Labels, People, Offset, Limit})` matches every word, the last as a prefix while someone types, and ranks in tiers: the exact issue key (old keys too) or the exact page title, then key and title matches, then body matches, then comment matches (leading to their subject), each tier by bm25 (key and title weigh more), then the newest. `Projects` and `Spaces` are what the person may read. A hit has its snippet as parts with the matched words marked (`search.Part`), which the page renders escaped in `<mark>`.
- `GET /search?q=&kind=&project=&space=&label=&person=&page=` is the results page (FR-57.2) with the kinds' counts; its results are the shared view `search:<params in base64url>`, keyed by the scopes the person reads and the params, listening to `search`, `issues`, `people` and the swap topics of the index's rebuilds (`search.ProjectionTopics`).
- The header's search box (FR-57.1): `views.SearchBoxAttrs()` on the input and `views.SearchSuggestSlot()` after it in the form (`ui.HeaderProps.SearchAttrs`, `SearchSuggest`). While someone types two characters or more, at most every 300 ms, the box asks `GET /search/suggest?q=`, a read that answers a patch of `#search-suggest` (a popover in the top layer, anchored under the box) with the first 5 issues and 5 pages and a link to every result; Down goes into it, Escape closes it, Enter submits the form to `/search`. A polite live region says how many suggestions there are.
- Rebuilds: a new version of one of the projectors makes lith's runner rebuild its tables into copies, FTS5 table included, and swap them in. Tested in `internal/search` (`TestRebuild`): the results of a fixed set of queries are the same before and after, the copies and the retired tables are gone, and searches that run while it rebuilds in batches of 10 answer from the old index, never empty (NFR-44). lith's copy takes the table's `CREATE VIRTUAL TABLE` statement and FTS5 renames its shadow tables with the table, so no projector of its own is needed.

## The demo

`internal/demo` runs tickit as a public demo (section 7 of the requirements).

- **Seed** (DM-02). `demo.Seed(ctx, w, content, run, epoch)` writes `internal/demo/seed`'s content with the commands people use, each by a seeded person with a past `By.At`: the people, the projects with their components, every issue as it was created (`Issue.Initial`), every change of its history, links, comments and watchers at their times, and at the end the board order (the fewest moves, by the project's lead). The steps run in time order, 64 to a writer command, so the log's positions follow the times and the history tabs and feeds read like 30 days. Ids are UUIDv7s whose time is a fixed day plus the thing's place in the seed and whose random bits hash its key, so every run gives the same ids and keys. It takes about 0.1 s. The wiki adds its spaces, pages, versions, page comments and templates as `Step`s with `demo.RegisterPageSeeder`, using the run's `SpaceID`, `PageID`, `PageCommentID`, `TemplateID`, `By` and `Doc`; without one, no page is seeded. `tickit seed` seeds a new database, `serve -dev` an empty one; production gets its content from the reset.
- **Reset** (DM-03). `Demo.Run` resets at 04:00 Europe/Zurich and touches `demo` ten minutes before; "Reset now" (`POST /cmd/admin/reset`) calls `Demo.Reset` too. A reset sets the flag that the guard reads, flushes the writer, waits until the catch-up projectors have handled every event, and then one command (`demo.Wipe`) deletes the rows of every table but `demo.Kept` (accounts, login sessions, preferences, the security and moderation logs, blocks, the demo's state, `lith_projections`, `lith_event_kinds`, `sqlite_sequence`) and the guests' rows of `people`, and bumps the epoch. The event log, the stream states and the inline projections empty in one transaction, so a rebuild after it equals the live tables; positions keep growing, so the projectors' checkpoints stay true; a projection copy of a rebuild under way empties too. The seed runs, the flag drops, and `hub.MarkAll` renders every view again. Until then no page sees the emptied or half-seeded tables: every view but the demo's, the tab's and the prefs' renders nothing (`web.Server.quiet`, which also drops a frame read while a reset began or ended, by `Demo.Quiet`), and a document answers 503 with "The demo is resetting" and loads again every 2 seconds (`views.Resetting`). A wipe of a full day takes about 10 ms. Every reset is a row of `demo_resets`, counted in `tickit_resets_total{outcome}` and `tickit_reset_seconds`.
- **Epoch** (MP-13.2). `demo.Epoch(ctx, q)` is bumped by every reset. A page keeps its id across resets but its stream starts anew, so the wiki's editor names the epoch it opened in with its edits and the wiki refuses an older one.
- **Guard.** `web.Server.run` wraps every action's command in `Demo.Guard`, inside `tabs.Act`: during a reset it fails with `demo.ErrResetting` (503, no outcome); a blocked guest's change is a denial with "Changes from this browser are paused." (403 and the outcome); a guest's creation past `demo.Caps` (1,000 issues, 300 pages, 200 images between two resets, counted in `demo_caps`) is refused with "The demo is full until the next reset". `tracker.CreateIssue` counts as an issue; the wiki names its page and image commands with `demo.CountCreations`.
- **Moderation** (DM-07). `demo.Moderate{Action, Kind, ID, Reason}` hides, restores or deletes one thing of a kind registered with `demo.RegisterModerated` (issues: `tracker.HideIssue`, whose `issue.hidden` sets `deleted_at` so the issue leaves every list, and `DeleteIssue`; comments: `HideComment`, `DeleteComment`; the wiki adds pages, page versions and images in `internal/demo/wiki.go`), checks `access.Moderate`, and writes `moderation_log` and the security log. A version (`wiki.HideVersion`, id `<page>.<number>`, the events `page.version_hidden` and `.version_unhidden`) leaves the history, compare and its own page for everyone but staff, and the newest is never hidden; an image of the library (`wiki.HideImage`, the table `hidden_images`) renders as "Image hidden by a moderator" wherever a document shows it (`doc.StaticResolver.Hidden`, touched on `chips:*`), and `/img/lib/<id>` answers 404. Reports (DM-08): `POST /cmd/report {kind, id, reason}` by anyone who reads the thing (`demo.Report`, the table `reports`, one open report per reporter and thing), listed first on `/moderation`; a hide or a delete closes the thing's reports, `POST /cmd/moderation/dismiss {report}` one. Every document holds the report dialog (`views.ReportDialog`); a button opens it with `views.ReportAttrs(kind, id)`. `Demo.Block` pauses a guest for 24 hours by person id (`blocks`) and by the client address they last acted from, kept in memory only (NFR-25.2).
- **Pages.** `/moderation` (moderators and site admins; the view `moderation:`, topics `issues`, `moderation`, `people`, `pages`), `/admin` with the tabs Accounts (`admin-accounts:<filter>`; a site admin erases an account there, `POST /cmd/admin/erase`, `people.EraseAccount`, NFR-27.1), Guests, Statistics (`admin-stats:`, every 5 s, with the 20 view keys rendered most, keys that hold a tab id as a hash, MP-11.4), Security log and Demo (`admin-demo:`), and `/account` for an account's password and sessions. Everyone without the right gets 403, the views too. An account whose first password an admin set (`must_change_password`) is sent to `/account` from every page, and its actions answer 403 until it changes it.
- **Uploads** (FR-85, NFR-15). `internal/images` keeps uploaded images as rows of `uploads` (migration 082): the bytes encoded again, the media type, the size, the subject (a page or an issue) and who uploaded it when. The editor posts a file to its host's `upload` attribute, `data-cmd` and `/image`: `POST /cmd/pages/{id}/image` or `/cmd/issues/{id}/description/image`, a multipart body with `tab`, `op` and `file` (`routes_images.go`). The handler checks the class "upload", reads the body in memory, checks the right from a read, converts the file outside the writer (`images.Process`: sniffed by its bytes, its header at most 5 MB and 4,096 by 4,096 pixels, one conversion at a time, a JPEG turned by its orientation, PNG or JPEG out) and runs `images.Upload` through `tabs.Act` and the guard, which checks the subject again (`wiki.DocEditable`, `tracker.DescriptionEditable`), the caps (20 images and 50 MB a person, 500 MB in all, between resets; the guard counts each against the 200 images of guests) and answers `{id, width, height}` as JSON; a refusal answers its message as text (413, 422, 403, 429, 503). The id is `up-` and 128 random bits in base32 (`images.NewID`), a document's image id like a library one's: the commit's rules take an uploaded id that exists (`collab`'s rules in the writer), and `/img/lib/<id>` serves it (`uploadedImage`) with its media type, `nosniff`, a sandbox CSP and a private year-long cache. Moderators act on the kind "upload" (`internal/demo/images.go`): a hide is `wiki.HideImage`, which takes uploads too, and a delete hides it and removes its bytes (`images.Delete`). Every upload, hide and delete touches `images` (`images.Topic`), which the moderation view lists. A reset empties `uploads` with the rest.
- **Word list** (DM-06.4). `internal/demo/words.Blocked` checks display names (`people.Rename`), labels, and project names and keys; the wiki checks space names with it. The list is ROT13-encoded in `words.txt`.

## The edge

`web.Server.Handler` puts the edge around the routes, inside out: the actor (`people.Middleware`), `edge.Sessions` (`__Host-sid` with `-secure`), `edge.CSRF` with `Datastar: ["POST /cmd/", "POST /pace", "POST /ack"]` and no exemptions, `edge.SecurityHeaders` with `DefaultCSP` and HSTS with `-secure`, `X-Robots-Tag: noindex, nofollow`, `edge.Compress`, `edge.Recover`, `edge.LogRequests` (its lines name a page by its id, with the slug written as `-`, and `/labels/<name>` as `/labels/-`, so the log holds no text of issues, pages or comments: `web.LogPath`, NFR-28). `GET /static/` skips the session and the actor (the security headers, the log and recovery stay): its answers are public and immutable, precompressed by `edge.Static`, and a cookie on one would go to everyone a shared cache gives it to. `cmd/tickit` mounts `/healthz` and `/readyz` beside it (`/readyz` waits for the database, the writer, the hub, the runner and the static files' compression, `edge.Static.Warmed`) and serves metrics on a loopback listener of their own (`-metrics`, 127.0.0.1:7205). Pages register with `s.get(pattern, handler, probes...)` and actions with `s.post`, which refuses anything outside `POST /cmd/`.

## Frontend

- The design system lives in `internal/ui` (templ components) and `internal/web/static/css/` (tokens first, then base, then components, then one file per area). Pages use tokens, never raw colours or sizes. `/design` renders every component, in light and dark.
- Starbase components are vendored under `internal/web/static/vendor/starbase/`; tickit's own Rocket components (`sb-rich-editor`) are built from `editor/`.
- Datastar expressions live in Go constants (`internal/views/expr.go` and per-area files). No value from a person goes into an expression or a script (NFR-13); it reaches the page as escaped HTML or as a signal.
- A frame never moves the focus or resets a field (MP-03.3): regions are siblings, fields are in the frame or `data-ignore-morph`, and the document keeps the focused element where it is on screen when a frame changes the layout above it (`views.keepPlace`, a `ResizeObserver` on `<body>`), which the browser's scroll anchoring does not, as it holds the first visible element instead.
- Every page works by keyboard (NFR-47), at 320 CSS pixels (NFR-46), with `lang="en"` and English relative times whose title is the absolute time (NFR-51).

## Tests

- `go test ./...` runs everything that needs no browser. The race detector is slow: run `go tool task test-race` at milestones, not after every change.
- Every decider has `eventstest` cases; every event type a JSON sample in `testdata/<kind>/<type>.json` checked by `eventstest.Samples`; a test rebuilds every read model from the events (FR-155.2).
- `internal/web/webtest` runs the server in process behind the whole edge, opens a stream, posts an action as a browser would (Datastar and `Sec-Fetch-Site` headers) and reads frames; `internal/dbtest` runs commands against a fresh database and records the topics they touch.
- GET never writes (NFR-06): every GET route registers with `s.get` and a probe URL (a pattern with wildcards needs one), and `TestGetNeverWrites` requests every probe as four kinds of visitor and compares a fingerprint of every table before and after. An area that adds a page with an id in its path gives a probe that names something its test data holds.
- The security suite (`docs/security.md`, `go tool task security`) sends every registered action as each kind of person without its right and with it, from other sites and with malformed bodies, and every GET and view kind as every kind of visitor; an action without a case in `secCases` (`internal/web/security_test.go`) fails it. Every `webtest` server's log is searched for the passwords and session ids its test sent (NFR-11).
- `e2e/` drives real browsers with `internal/browsertest`; it skips when no Chromium is found (`CHROME` names the binary; `/usr/bin/chromium` on the development machine).
- `cmd/tickit-load` is the load test of NFR-38 (`go tool task load`): `gen` writes 10,000 issues, 2,000 pages and 1,000,000 events through the commands with the runner going, and `run` starts the binary as a process of its own with the unit's `GOMEMLIMIT`, opens 200 streams as browsers do, sends the actions, restarts the server and reports per requirement; the numbers are in `benchmarks/RESULTS.md`. A binary built with `-tags pprof` serves `/debug/pprof/` on its metrics listener for `run -cpuprofile`.
- Timing tests (`TestSearchSpeed`, `TestBoardLoad`) skip with `-short` and under `-race` (each package's `raceDetector`, true in a test file built with the `race` tag).
